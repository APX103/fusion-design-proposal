# 从 x-IMU3 固件逆向看 quat-zupt-ekf 的提升空间

**对照对象**：`..`（本目录的原始实现）（七状态全量 EKF + ZUPT，Python/C99）
**证据来源**：`../ximu3-re`（x-IMU3 v2.6.0 固件逆向，PIC32MZ / Madgwick AHRS）
**本目录交付**：`ekf7plus` Python 包（提升方向的参考实现）+ `demo_compare.py`（同数据对比实验）

---

## 1. 两个工程的联系：同一套"三层防漂移"哲学

把 x-IMU3 固件（逆向结论）和 ekf7 逐层对照，会发现它们是**同构的**——
两个工程在解决同一个问题时收敛到了同一架构，只是观测器不同
（Madgwick 梯度下降 vs 7 状态 EKF + ZUPT）：

| 层 | x-IMU3 固件（逆向证据） | quat-zupt-ekf（源码位置） |
|---|---|---|
| ① 上电初始化窗口：静置均值 → 零偏 + 初始姿态 | 状态机 `0x9D07BFA4`：累加器 ×1/N 取均值，状态 0→1→2；窗口长度 @+0x34；陀螺均值→零偏（即设置项 `gyroscope_offset_correction_offset`），加计/磁计均值→初始姿态 | `auto_calibration.py` 三窗均值（预置/累积/收尾）+ `navigation_filter.py` 阶段 1（0.1–3 s 静置均值）——**几乎逐字段同构** |
| ② 运行中观测 + 卡方/幅值门控 | 加计/磁计抑制计数器（@+0x6c/+0x70、+0x84/+0x88），cos² 阈值比较，违约步进 **−9**、恢复触发重接纳（0x9D036FD0–0x9D037004） | `observations.py` 卡方式门控（ZUPT 逐轴、磁航向 1 维） |
| ③ 辅助机制：静止检测 / 超量程恢复 / 初始化增益斜坡 / 锚定航向 | +0x54/+0x58 斜坡倒计时；\|ω\|>2000°/s 触发重斜坡（+0x1c）；磁航向锚定 + cos² 截止（0x9D0370EC）；时间戳 dt（0x9D038AB0，±0.3% 时基误差校正） | `motion.py` 三级静止检测；`parameters.ang_rate_bias_k` 零偏平滑；固定 `dt=1/fs` |

**结论**：ekf7 的整体架构选择与商业产品（x-io）的工程实践互相印证，方向没有问题。
提升空间不在"推倒重来"，而在**六个具体机制**上。

## 2. ekf7 已经做对的（保持不动）

- ZUPT + 磁航向的可观测性设计（六轴 yaw 缓漂是原理性的，不是 bug）；
- 逐拍差分黑盒验证方法论（README 验证一节）——这比多数开源 IMU 工程严谨；
- Python/C99 双实现同源。

## 3. 六个提升方向（P1–P6，按收益排序）

### P1 陀螺零偏进状态向量（收益最大）
- **x-IMU3 证据**：零偏是 AHRS 引擎的常驻状态（+0xa0 区，`AhrsUpdate` 每拍读写），不是外部估计量。
- **ekf7 现状**：零偏在滤波器**外**——`pipeline.gyro_bias`（自标定一次性）+
  `ang_rate_bias_k=0.04` 指数平滑（`navigation_filter.py` 静止期才更新）。
  后果就是 README 已知局限 1：**匀速旋转被误判静止 → 零偏被污染 → yaw 冻结**。
  污染路径正是"静止检测器驱动零偏更新"这一环。
- **改法**：误差状态 EKF 里把 δb 放进状态（P1 与 P2 绑定），由重力/磁观测经
  协方差自然估计，静止检测器退化为只控制 ZUPT 开关——污染路径被结构性移除。

### P2 全量式 → 误差状态式（ES-EKF）
- **ekf7 现状**：7×7 协方差直接在四元数全量上传播（README 已自认数值弱项）。
- **改法**：名义状态（q, v, b）+ 9 维误差状态（δθ, δv, δb）。四元数天然归一
  （不需要每拍 `quat_normalized` 修正），F 稀疏（δb 行是单位阵），姿态误差局部
  参数化无奇异。这也是 x-IMU3 对应机制的"正确 EKF 化"。

### P3 重力矢量观测：运动中持续修正俯仰/横滚（x-IMU3 最核心的机制）
- **x-IMU3 证据**：加计观测**每拍参与**（对象 +0x48 存样本、五处归一化之一），
  只在创新超限时被抑制计数器逐出、恢复触发后重新接纳——不是"静止才用"。
- **ekf7 现状**：运动中**没有任何直接的姿态观测**（ZUPT 只观测速度，
  姿态靠速度耦合间接修正；九轴只有航向 1 维）。俯仰/横滚在长运动段
  只能靠陀螺+协方差撑着。
- **改法**：单位重力矢量观测 z = f/‖f‖，H=[[(Rᵀẑ)×] 0 0]，NIS 门控
  （χ²₃）+ |‖f‖−g| 自适应 R。**这是本次提升的主菜**——demo 里能看到差别。

### P4 拒绝滞回（x-IMU3 的 recovery trigger 移植）
- **x-IMU3 证据**：违约样本计数 −9 递减、低于恢复触发限值才重新接纳
  （0x9D036FD0 一带的 slt/movn 序列）——门控带**滞回**，不会抖动。
- **ekf7 现状**：逐拍硬门控（超限即拒、下拍即收），磁干扰交替时容易
  在门限附近抖动。
- **改法**：`gating.py` 实现带恢复触发的拒绝计数器（步进常数保留 −9 以示出处）。

### P5 时间戳 dt（可变步长）
- **x-IMU3 证据**：每样本硬件时间戳 → 64 位双精度 dt（0x9D038AB0），
  手册明说这是"±0.3% 采样率误差独立于测量"的实现。
- **ekf7 现状**：`dt = 1/fs` 固定。真实 IMU 时钟偏差 + 丢包时会系统性漂移。
- **改法**：`calculate(..., dt=None)` 逐拍可选 dt，缺省回落 1/fs。

### P6 初始化增益斜坡（小项）
- **x-IMU3 证据**：初始化斜坡 +0x54/+0x58（前 N 拍高增益收敛），
  复位时 `AhrsReset` 重新装填。
- **ekf7 现状**：三段式初始化已有等价物，但斜坡只作用于观测调度。
- **改法**：对准后前 `ramp_n` 拍把重力观测 R 从 ×4 线性降到 ×1（保守实现）。

### P7 温度-零偏联合估计（新增；回答"能不能加电热管恒温"）

**先回答一个事实问题：两边都没做温漂处理。**
- quat-zupt-ekf 全仓库（Python/C99/文档）搜不到 temperature/thermal 相关代码，
  输入接口只有 acc/gyro/mag；
- x-IMU3 固件同样没有：温度只用于**上报**（`temperature_message_rate_divisor`，
  5 Hz）和电池充放电保护；设置注册表里没有任何温度系数；
  手册原文 *"Calibration is performed at room temperature. Accuracy will be
  reduced for operating temperatures that deviate from this temperature."*，
  各精度表脚注 *"Accuracy is specified for the calibrated temperature only."*

恒温（电热管 + 测温 + PID 稳在 45°C）是有效的硬件路线，但在电池供电的
x-IMU3 类产品上代价很高。三条路线对比：

| 路线 | 原理 | 代价 | 适用 |
|---|---|---|---|
| A. 硬件恒温 | PID 把 T 压成常数 | 功耗、预热时间、封装内温度梯度、体积 | 有线/工业/高精度 |
| B. 出厂温箱标定 | 每台测 b(T)，运行时查表 | 产线成本 | 有产线条件的产品 |
| C. **在线联合估计（P7）** | 把温度斜率 k 作为 EKF 状态，边用边学 | 纯软件；需温度输入与温度激励 | 改造现有产品性价比最高 |

- **x-IMU3 证据（可复用性）**：它已经内置温度传感器（5 Hz、±1°C），
  固件里 `Temperature Message` 每拍可读——**只差把 T 接进滤波器**。
- **改法**：误差状态从 9 维扩到 12 维 `[δθ, δv, δb0, δk]`，零偏模型
  `b(T) = b0 + k·(T − T_ref)`；F 中 δθ̇ 对 δk 的耦合项为 `−(T−T_ref)·I`。
  温度激励（开机自热、环境波动）使 b0 与 k 可分离，等效于在线学习
  每台设备的 b(T) 曲线，替代出厂温箱标定或硬件恒温。
- **实现**：`esekf.py`（thermal=True 走 12 状态）、`pipeline.calculate(..., temp=)`。

### P8 硬件恒温 + 温态标定（抄自 ATOM-IMU，`../03-atom-imu`）

**来源**：`xrobot-org/atom-sdk`，V5.3 固件（STM32G431KB）。固件镜像为 XXTEA-CTR 加密，
已从 bootloader 提取密钥并完整解密（方法与证据见 `../03-atom-imu/docs/ATOM_IMU_逆向笔记.md`）。

固件确认的做法：
- 每颗 IMU 配加热电阻 + PWM；`set_temp` 目标温度**钳位 10–80°C**，双 IMU 同步；
- 温度稳定性判据：环形缓冲均值 + **平均绝对偏差 < 0.13°C**（FUN_0800F444）；
- 标定入口被稳定标志门控：不稳定直接报 `Temperature is not stable!`；
- 流程：预热 10 min → 4 姿态静置 ≥1 min/姿态 → 保存零偏/安装 → `test` 测零漂；
- 指标：yaw 零漂 < 10°/h，良好环境 < 3°/h。

**移植**：`atom_scheme.py` 提供 `ThermalPlant`（一阶热模型）、`PIController`
（抗积分饱和）、`TempStabilityDetector`（与固件同构，阈值 0.13°C）、
`MultiPoseCalibration`（陀螺零偏均值 + 加计 12 参数 LS）、状态机
`WARMUP→STABILIZE→CALIBRATE→READY`。

**与 P7 的关系**：P8 是硬件路线（把 T 变成常数），P7 是软件路线（把 T 变成可测量）；
两者可叠加。不想加加热电阻时用 P7；有供电条件且追求极致时用 P8，再叠加 P7 反而
能补偿恒温残差。

**明确不做**：x-IMU3 的 15 参数出厂标定不在本提案内（那是生产线问题，
不是算法问题；ekf7 的安装矩阵自标定已覆盖使用侧需求）。

python3 demo_atom_scheme.py        # P8 恒温方案对比

实验设计（公平性）：
- 同一份合成数据流（200 Hz，与 ekf7 demo 同参数：初始倾斜 5°/−3°、
  恒定陀螺零偏、加计/陀螺/磁噪声）同时喂两个管线；
- 场景 A（ekf7 的设计场景）：静置 → 往复偏航 → 静置，含一段磁干扰突发；
- 场景 B（ekf7 的已知弱点）：静置 → **匀速旋转 30°/s** → 静置；
- 误差评估统一用 ekf7 自己的 `quat_to_euler`（同一约定，零偏置）。

## 5. 实测结果（`python3 demo_compare.py`，合成数据，200 Hz）

同数据、同评估窗（t>8 s，双方均完成初始化；基线按它自己 demo 的方式合成安装矩阵）：

| 场景 | 指标 | ekf7 基线 | ekf7plus |
|---|---|---|---|
| A 设计场景 | roll RMS | 0.018° | **0.005°** |
| （往复偏航） | pitch RMS | 0.013° | **0.005°** |
| | yaw RMS | 1.310° | **0.934°** |
| A 磁干扰段 | yaw RMS | 1.370° | **0.019°** |
| B 匀速旋转 30°/s | yaw RMS | 102.75° | **0.42°** |
| （README 已知局限 1） | yaw max | 179.97° | **1.24°** |
| | 零偏 z 估计 | **+345 mrad/s（被污染）** | +1.17（真值 +1.5） |

两个关键机制被数据证实：

1. **P3 重力矢量观测**：场景 A 运动中俯仰/横滚 RMS 从 0.013–0.018° 降到约 0.005°，
   姿态观测不再依赖静止检测；
2. **P1 零偏进状态 + 与静止检测解耦**：场景 B 中基线把匀速旋转判成静止
   （运动段 flag≥3 占比 **81.2%**），零偏 z 被污染到 +345 mrad/s、yaw 冻结/翻转
   （最大误差 180°）；ekf7plus 的零偏与姿态全程保持（yaw max 1.24°）。
   这正是 README 自述局限 1 的量化复现，且被结构性规避。

补充：场景 A 中基线的静止误判率也有 71%（往复运动经过转向点时瞬时角速率趋零），
但此时"冻结"与真实运动差别小，误差不显著——该缺陷只在**持续匀速旋转**下有害。

### P7 温度补偿实测（`python3 demo_thermal.py`，100 Hz，120 s）

温度 25→45°C 开机自热 + 环境波动；磁干扰段 45–75 s（磁航向被门控拒绝，
零偏变化只能靠模型预测）：

| 方案 | yaw RMS 全程 | yaw RMS 磁干扰段 | yaw max 干扰段 | 末端零偏误差 |
|---|---|---|---|---|
| ① 无温度补偿 | 3.79° | 3.28° | 5.95° | 5.26 mrad/s |
| ② P7 软件补偿 | **2.38°** | **2.39°** | **3.43°** | **0.12 mrad/s** |
| ③ 理想恒温炉（T≡45°C） | 2.39° | 2.39° | 3.40° | 0.00 |

②的斜率估计 `k = [+0.602, −0.502, +0.806] mrad/s/°C`，真值
`[+0.600, −0.500, +0.800]`，误差 0.006。

**结论**：在本场景中，**软件温度补偿达到与理想 45°C 恒温炉几乎相同的精度**，
但不需要加热功耗、预热时间和封装内温度梯度。你的电热管方案本身成立
（③就是它的上限参照）；如果目标是改造现有产品，优先做 P7——
x-IMU3 已经内置温度传感器，缺的只是把它接进滤波器。

### P8 恒温方案实测（`python3 demo_atom_scheme.py`，100 Hz，480 s）

真值零偏 `b(T)=b0+k(T−25)`，k=[0.6, −0.5, 0.8] mrad/s/°C；ATOM 方案目标 45°C：

| 方案 | 稳定耗时 | 标定后零偏误差 | 末段积分零漂 |
|---|---|---|---|
| ① 无恒温（自热 20→38°C，60 s 室温标定） | — | 0.29 mrad/s | **−34.62 °/min** |
| ② 恒温 45°C + 稳定后标定（ATOM 方案） | 89.4 s | **0.03 mrad/s** | **−0.39 °/min** |
| ③ 恒温 45°C 但 60 s 就标定（不等稳定） | — | 0.20 mrad/s | −2.33 °/min |

**结论**：ATOM 的"恒温 + 等稳定再标定"在本仿真中把零漂从几十 °/min 压到亚 °/min；
③ 说明**光有加热不够，必须等热平衡**（固件用 10 分钟预热 + 0.13°C 判据保证这一点）。
实机热时间常数远大于仿真，所以官方流程是 10 分钟而不是 90 秒。

## 6. 局限

- ekf7plus 是**机制验证参考实现**（约 1100 行），未做 C 移植与整定扫参；
  参数默认值只做了粗调；合成数据不能替代真机数据集回归。
  接入真项目时建议保留 ekf7 的差分验证方法论，对 ekf7plus 重复同样的
  Python/C 双实现流程。
- P8 的加热控制律未与 ATOM 固件逐行对齐（固件应用层控制循环未完整定位，
  移植采用标准 PI）；多姿态标定算法同样按标准 12 参数模型实现，未声称与固件一致。
- P8 仿真中的真值 k 系数量级（0.5–0.8 mrad/s/°C）为演示设定，实机需辨识。
